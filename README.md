# jdelta

**English** | [한국어](README.ko.md)

**JVM Semantic Delta Engine**: tells you what a change *semantically* changed in a JVM project, what it can affect, and what should be redone first.

```text
$ jdelta impacted-tests main
1  OBSERVED  com.acme.core.PriceCalculatorTest#calculatesRoundedTotal()   PriceCalculator#round(long) -> executed by this test
2  OBSERVED  com.acme.app.CheckoutServiceTest#checksOut()                 PriceCalculator#round(long) -> executed by this test
3  OBSERVED  com.acme.pricing.DiscountsTest#appliesPercent()              PriceCalculator#round(long) -> executed by this test
```

After a one-line change to a private method, only 3 of the 9 tests across 3 modules actually executed that method, so only those need to run first. Every decision comes with a reason path and a confidence level.

---

## Why it is needed

Slow builds, slow tests and long CI runs in JVM development share one root cause:

> **JVM tooling does not know precisely what a change can actually break.**

When it does not know, it redoes everything to be safe.

```text
one-line change in a private method body
  -> recompile the module
  -> recompile downstream modules
  -> run the whole test suite
  -> rerun the whole CI job
```

Existing tools answer at the granularity of **files, tasks, modules and test classes**. But the same "file changed" can mean very different things.

| Change | What it actually means | What typical tools see |
|---|---|---|
| private method body | Only tests that executed that method are affected. Other modules need no recompilation | File changed → whole module |
| Comments, moved lines | The classfile is semantically identical. Nothing is affected | File changed → whole module |
| `public static final` constant value | **The old value is inlined into callers' classfiles.** Unless dependent modules are recompiled, the old value is used at runtime | Dependent modules may stay as they are |
| Kotlin public `inline fun` body | **The body is copied into callers.** Calling modules must be recompiled | Same signature, so no ABI change |
| `@JsonProperty("sku")` → `"code"` | Compilation is unchanged, but framework behavior read through reflection changes | No impact |
| Field added to a MapStruct input DTO | Code generated by the annotation processor may change | Invisible |

`jdelta` tells these apart by combining **semantic comparison of classfiles** with **recorded test executions**.

## What makes it different

### 1. It compares meaning, not files

It compares compiled output (classfiles), not source text, and splits each change by ABI layer.

- **compile ABI**, **binary ABI**, **reflection ABI** and **framework** impact are judged separately
- Method body hashes normalize line numbers, local variable tables and lambda numbering, so adding a comment or a lambda produces zero false changes
- It models the corners of the JVM: public members inherited from package-private superclasses, synthetic bridges, `$default` methods
- It reads Kotlin metadata to tell `internal` (public on the JVM but invisible outside the module), `inline`, and nullability, parameter name and default value changes apart

### 2. It selects tests by observation, not guesswork

`jdelta record` uses a Java agent to record **which methods each test method actually executed**. Impact analysis follows this trace together with a static graph (calls, fields, inheritance, inlining).

- The trace avoids walking the static call graph upward forever until "almost every test is impacted"
- Code that **runs only once**, such as `<clinit>`, `@BeforeAll` and a cached Spring context, is tracked separately
- Tests without a trace, including newly added tests, are **always included**

### 3. It says when it does not know

Every decision carries a confidence level.

| confidence | Meaning |
|---|---|
| `EXACT` | Known deterministically, e.g. a descriptor diff or classfile ownership |
| `OBSERVED` | Actually observed in a test execution trace |
| `INFERRED` | Inferred from framework rules or static analysis |
| `CONSERVATIVE_UNKNOWN` | Included because it could not be safely excluded |

A classfile change the analyzer cannot explain is not silently ignored; it is reported as `UNKNOWN`. When most selected tests were included conservatively, the report says directly that impacted-first is of limited use for this change.

### 4. It never skips tests (impacted-first)

Wrongly skipping a test is fatal, so v0.1 does not skip.

```text
1. Run the impacted tests first   -> fast failure signal
2. Then run the full suite        -> safety is preserved
3. Compare both results and record missed failures -> confidence is measured
```

Even when phase 1 fails, the full suite runs to the end and the build fails afterwards. The recorded misses are the data that will justify an opt-in skip mode later.

### 5. It does not change your build

It is not a new build tool. It works alongside Gradle.

- It injects its plugin through an init script and reads the project structure (including `api` vs `implementation`) without any build script changes
- The agent has zero runtime dependencies (ASM is relocated), so it does not clash with your classpath
- Results come as Markdown for people and JSON for machines

## Demo scenarios

Verified with real Gradle builds in `samples/acme-shop` (Java + Kotlin, 3 modules, MapStruct). Rerun them with `./gradlew :jdelta-cli:e2eTest`.

| # | Change | What jdelta reports |
|---|---|---|
| 1 | private method body | No compile ABI change. Selects only the 3 tests that executed the method (`OBSERVED`) |
| 2 | public method signature | Recommends downstream recompilation. The changed test itself ranks first (`EXACT`), then tests of downstream callers |
| 3 | Kotlin public inline body | `KOTLIN_INLINE_BODY_CHANGED`: calling modules must be recompiled; already compiled callers run the old body |
| 4 | `public static final` constant | Recommends recompiling callers that inlined the value. The impact cannot be bounded, so tests are included conservatively and the report says so |
| 5 | runtime annotation value | Compile ABI unchanged, framework impact `RUNTIME`. Tests that executed the class (`INFERRED`) |
| 6 | MapStruct input DTO | Explains that generated code may change and conservatively includes tests that executed the generated class |

Report excerpt (scenario 3):

```markdown
### 2. `com.acme.pricing.MeasureKt#measured(String, Function0)` — KOTLIN_INLINE_BODY_CHANGED
| compile ABI | **downstream** |
| binary ABI  | runtime only   |
- Why: inline function body changed; the body is copied into callers, which keep the old copy until recompiled

## Test Impact
| 1 | `com.acme.app.CheckoutServiceTest#checksOut()` | OBSERVED | CheckoutService#checkout(Order) → CheckoutServiceTest#checksOut() |
```

## Getting started

Requires JDK 17 or later.

```bash
./gradlew :jdelta-cli:installDist      # jdelta-cli/build/install/jdelta/bin/jdelta
```

In the Gradle project you want to analyze:

```bash
# 1. On the baseline (main): store a build output snapshot and a test trace
jdelta snapshot --build
jdelta record -- ./gradlew test

# 2. After your change: semantic changes since the merge-base + impacted tests
jdelta diff main --build                 # Markdown report (--format json)
jdelta impacted-tests main               # ranked (--format json | gradle-filter)
./gradlew test $(jdelta impacted-tests main --format gradle-filter)

# 3. Or run impacted-first from Gradle
./gradlew test -Pjdelta.impactedFirst=true -Pjdelta.home=<jdelta distribution> -Pjdelta.base=main
```

In CI, keep `jdelta snapshot --out snap/` as an artifact of every main build and use it in PR builds with `jdelta diff --baseline-dir snap/`. Without a snapshot, `--build-baseline` builds the baseline in a temporary git worktree. You can also compare two output directories without git (`jdelta diff --base-classes ... --head-classes ...`).

`.jdelta/` is a cache that can always be rebuilt; add it to `.gitignore`.

## Status and limitations

The v0.1 implementation (steps 1–16 of ARCHITECTURE.md §14) is complete. Output schemas are still unstable.

- Supported: Gradle, Java/Kotlin, JUnit 5 (partly JUnit 4); framework profiles (Spring, Jackson, JPA, MapStruct, Lombok) as annotation-based rules
- There is no test skip mode. The full suite always runs
- For constant changes, jdelta cannot pick out the classes that use the old value, so it conservatively widens to all dependent modules
- `jdelta record` supports Gradle commands only. Maven and IDE integration do not exist yet
